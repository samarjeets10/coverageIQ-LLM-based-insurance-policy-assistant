# CoverageIQ — Synthetic Recommendation Dataset (`data/`)

> **DISCLAIMER:**
> This dataset contains synthetic development records. Its relevance labels are generated using predefined rules and do not represent real customer preferences or validated insurance suitability decisions.

---

## 1. Purpose

This directory contains reproducible, schema-aligned synthetic Indian insurance datasets generated by [`ai_service/recommendation/dataset.py`](../ai_service/recommendation/dataset.py) for Stage 3 of **Module 6A (Policy Recommendation)**.

The dataset supports development, controlled experiments, and automated testing of:
1. Deterministic Hard Filtering Engine (Stage 4)
2. Feature Engineering Pipeline (Stage 5)
3. LightGBM Ranker Training (Stage 6)
4. XGBoost Ranker Training (Stage 7)
5. Ranking & Model Evaluation (Stage 8)
6. End-to-end `POST /api/v1/recommend` and `POST /ai/recommend` integration tests (Stage 9)

**Database isolation:** These CSVs are self-contained and are **not** inserted into PostgreSQL.

## 4. Label Generation Methodology

### Stage A — Mandatory Eligibility Gate (`evaluate_eligibility`)
A `(profile, policy)` pair receives `is_eligible = True` **only if zero mandatory rules fail**:
1. Active catalog policy (`policy_status == "active"` and `is_catalog_eligible == True`)
2. Policy type compatibility (`policy.policy_type == profile.preferred_policy_type`)
3. Entry age within `[min_entry_age, max_entry_age]`
4. Applicant type permitted in `eligible_applicant_types`
5. Coverage mode (`individual` / `family_floater`) and `family_size <= max_family_members`
6. Budget overlap (`annual_premium_min <= budget_max` and `annual_premium_max >= budget_min`)
7. Coverage adequacy (`sum_insured_max >= min_sum_insured`)
8. Geographic availability (`pan_india_coverage` or `geographic_location` in `available_regions`)
9. Tenure bounds (`min_tenure_years <= tenure_years <= max_tenure_years`)
10. Lifelong renewal requirement when requested
11. Co-pay (`copay_pct <= max_copay_pct`) and deductible (`deductible_amount <= max_deductible`) ceilings
12. Waiting periods & PED coverage (initial waiting days, PED coverage & waiting months, condition not in `exclusions`)
13. Room-rent preference, cashless availability, and minimum network count
14. All `required_benefits` present in `covered_benefits`
15. Category-specific eligibility (Car `vehicle_types` & `vehicle_age_limit_years`; Term `non_smoker_only` restriction)

If `is_eligible == False`, `suitability_score = 0.0` and `relevance_label = 0` unconditionally.

### Stage B — Graded Preference Scoring (`compute_suitability_score`)
For eligible pairs only, `suitability_score` combines 5 normalized sub-scores weighted by `profile.risk_preference`:

| Component | `balanced` | `low_premium` | `comprehensive_coverage` |
|---|---|---|---|
| Affordability vs `budget_max` | 0.25 | 0.40 | 0.12 |
| Sum insured headroom | 0.20 | 0.15 | 0.23 |
| Benefit richness + restoration + NCB | 0.20 | 0.15 | 0.27 |
| Low co-pay / deductible / waiting periods | 0.15 | 0.15 | 0.18 |
| Insurer claim settlement ratio + network | 0.20 | 0.15 | 0.20 |

## 5. Data Leakage Prevention & ML Consumption Plan

1. **Group-Aware Splitting:** Train/validation/test splits in Stages 6–8 **must group by `profile_id`** (`GroupShuffleSplit` / `GroupKFold`) so no user profile appears in both training and evaluation folds.
2. **Identifier Exclusion:** `profile_id`, `policy_id`, and `policy_code` are grouping/join keys only and must **never** be passed as predictive features to LightGBM or XGBoost.
3. **Eligibility vs Ranking Separation:** Hard filtering (`is_eligible`) is executed deterministically before ML ranking. Rankers are trained and evaluated on surviving eligible candidates (`is_eligible == True`) using ranking metrics such as **NDCG@3 / NDCG@5** and **Precision@K** computed per `profile_id` query group.
4. **No Future Information:** Every component in `compute_suitability_score` uses only profile inputs and policy catalog attributes available at inference time.

## 6. Validation Rules & Known Limitations

### Validation Rules Enforced (`dataset.py`)
- Minimum counts (`>= 50` policies, `>= 20` profiles) and all 4 categories present
- Non-null unique `policy_id`, `policy_code`, and `profile_id`
- Valid age, premium, sum-insured, and co-pay ranges
- Every profile validated through Pydantic `UserProfileRequest`
- Referential integrity (zero orphan `profile_id` or `policy_id` rows)
- Strict separation invariant (`is_eligible == False` implies `relevance_label == 0` and `suitability_score == 0.0`)

### Known Limitations
- All insurers, premiums, networks, and profiles are synthetic approximations for Indian insurance plans and **do not** reflect real actuarial pricing or underwriting quotes.
- Relevance labels come from a deterministic linear-utility heuristic over observable features; LightGBM/XGBoost models trained on this dataset verify ranking pipeline mechanics (feature extraction, group splitting, NDCG evaluation, inference) and must be retrained before production claims when real preference/conversion labels exist.
